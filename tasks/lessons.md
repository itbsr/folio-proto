# Lessons

## StrictModeの二重起動とrefガードの組み合わせは「2回目が動かない」バグを生む
- **失敗モード**: `useEffect`内で副作用（XHR送信・SSE購読など）を「一度だけ実行したい」という意図で`useRef`の真偽値フラグ（例: `hasStarted.current`）を使って二重実行を防いでいた。`<React.StrictMode>`は開発時、effectを「実行→クリーンアップ→再実行」と意図的に二重起動するが、refはクリーンアップを跨いで値を保持し続けるため、1回目の実行で立てたフラグが2回目の実行をブロックしてしまう。1回目の副作用はクリーンアップで即座に破棄（例: `xhr.abort()`）されるため、正味「何も実行されない」状態になる。
- **検知シグナル**: ブラウザDevToolsのNetworkタブで、本来完了するはずのXHR/fetchが送信直後（数十〜数百ms）に`(canceled)`となっている。本番ビルド（StrictModeの二重起動なし）では再現しない。
- **予防ルール**: effect内の副作用を「一度だけ」に制限したい場合、`hasStarted`のような永続フラグで安易にガードしない。クリーンアップ関数が前回の副作用を正しく破棄していれば、StrictModeによる2回目の実行はそのまま「本物の」実行として機能するはずなので、クリーンアップの実装を信頼する。真に一度きりの実行が必要な場合は、effect外部の状態（親コンポーネントの状態、モジュールスコープの完了フラグなど）で管理する。

## ローカル（wrangler dev）と本番（Cloudflare エッジ経由）ではリクエストボディのストリーミング挙動が異なる
- **失敗モード**: クライアント→Worker→オリジンとリクエストボディをストリーミング転送し、受信側のバイト数で進捗を出す設計が、本番でのみ「0% のまま→完了時に一括 100%」になった。Cloudflare エッジは WAF 検査のためデフォルトでリクエストボディを全量バッファしてから Worker へ渡すので、途中経過は経路上のどこからも観測できない。`wrangler dev` はエッジプロキシを通らないため、ローカルでは問題なくストリーミングされ気づけない。
- **検知シグナル**: 「ローカルでは動くが本番では動かない」+ 同一 SSE ストリーム上の他イベント（推論進捗など）は本番でもリアルタイムに届いている（= SSE 配信経路は正常で、リクエストボディの到達タイミングだけが異常）。
- **予防ルール**: リクエストボディの逐次到達（アップロード進捗、チャンク逐次処理など）に依存する機能は、エッジプロキシ（Cloudflare、nginx の `proxy_request_buffering` 等）のボディバッファリングを前提に設計する。バイト進捗が経路上観測できない場合に UI が凍結しないフォールバック（不確定表示）を最初から用意し、本番相当の経路での動作確認をリリース前に行う。恒久解消には Cloudflare Configuration Rules の Request body buffering「None」（2026-01 提供開始）等のインフラ設定が必要。
